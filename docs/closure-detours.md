# Closure detours and route filters

When the chosen route crosses a closure, the persistent action becomes **Find detour**. It selects an available clear alternative first, otherwise requests a new route with bounded directed exclusions from the current closure feed. Progress and failure stay visible inside the preview sheet. A successful detour is shown for review before starting. An unavailable service or an unverified result keeps the original route blocked and offers retry or a different stop. Closing the preview invalidates late responses.

The Worker first uses an existing owned NZ engine when configured. For directed exclusions it can fall back to the [FOSSGIS global Valhalla service](https://github.com/valhalla/valhalla#demo-server), which supports [exclude_locations](https://valhalla.github.io/valhalla/api/turn-by-turn/api-reference/#other-request-options). Normal requests continue through the existing routing path. No paid navigation API, key, account upgrade or new billable container is enabled. Public service availability is subject to fair usage, not an unlimited production SLA: the fallback spaces requests by 1.1 seconds per isolate, coalesces matching requests, caches results for 30 seconds, and bounds concurrent requests. Both the requested exclusions and current closure feed are checked against every returned detour. An engine ignoring an exclusion cannot produce an accepted result.

Client exclusions use `avoid=lon,lat,heading;...`, limited to 32 entries. The Worker validates coordinates and constructs fixed narrow road exclusions itself. Private routing credentials never go to the public service. Road projection uses the actual directed segment of a curved ramp. Mobile and Worker use a 35-metre matching corridor. A specifically named ramp notice does not block a clearly identified through-motorway step; ambiguous or corridor-wide closures remain blocking. Tests also preserve named ramp routes and closures spanning multiple ramps.

Driving filters operate locally on up to three engine-provided alternatives: recommended, fastest, shortest, no matched known cameras, and with known cameras. Changing a filter makes no network request. Explicit distance/camera choices retain otherwise valid alternatives outside the default ETA recommendation envelope. Filters have an empty state and a reset; a hidden route cannot remain the start target. Camera filters require loaded camera data and mean matches against that dataset, not a guarantee of complete camera coverage. The same controls are available on the free plan. Shorter/fastest comparisons refer to the returned alternatives, not every possible path in the road graph.

Regression checks cover NZ/AU detours without an owned engine, stale/local feed exclusions, ignored exclusions, upstream failure, rate/cache coalescing, adjacent ramp versus motorway matching, filter ordering and empty results, stop order, inline status and the detour action at phone width. A live request to the public global service returned three routes with exclusions during implementation; actual navigation behavior still depends on current road data and GPS.

Live regression: the active Queenstown Rd southbound on-ramp record `nzta:event:564259` was matched on the CBD-to-Airport Park & Ride North route. The Worker produced a verified detour of 27,039.8 metres / 1,614.9 seconds using the free fallback. Mainline steps following motorway-to-motorway interchange instructions were checked separately from local-street ramp access. This check used a retrieved official snapshot, not a guarantee of live feed freshness.
